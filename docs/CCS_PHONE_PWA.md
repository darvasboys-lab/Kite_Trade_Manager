# CCS Phone — experimental native-style web frontend

Stop existing CCS before launch. From the existing Android Debian checkout:
```sh
cd /root/CCS
source .venv/bin/activate
python -m dhan_visual.phone_server
```
Open exactly http://127.0.0.1:8502. No Streamlit frontend is used. Do not expose the server to LAN/internet or run desktop CCS concurrently. Existing Python dependencies still apply. The local server has one unlocked vault per process; lock it in Settings or stop the server when finished. Existing encrypted vault is reused. Official FYERS sample redirect + full URL paste is supported; no biometric or daily auth bypass. No plaintext credential storage or broker order routes. No offline data caching.

This candidate is deliberately not a complete replacement: the native-style frontend supports FYERS vault, foreground automatic batched scan, shortlist/technical details, R1 check, futures, CE/PE option-chain viewing, covered-call accumulation plan and hypothetical trade tracking. Short-straddle and arbitrary multi-leg payoff building, Dhan/public provider parity, historical shortlist persistence, full CSV export, automatic callback, and full desktop parity remain outstanding. Use desktop CCS for these. Test 320/360/390/430 px, Android Chrome standalone install, real authorized FYERS connection, scan pacing, missing/stale quotes, every page and desktop regression before merge. No live broker tests have been performed by this change.

On launch, load catalogue expiry months automatically; once FYERS is unlocked and connected, verify available months with FYERS and select the nearest available expiry by default. Start with contract size below ₹7 lakh, premium strictly above 2% and all R1 statuses. Reuse matching same-day snapshots. Subsequent batches run only while Home is visible, with at least 60 seconds after completion; pause/resume is available. No automatic retry after a broker error. Manual Apply filters refreshes the scan subject to the same cooldown. Tests are included but device and broker validation remain outstanding.

### Optional fingerprint/device unlock (experimental)
Open http://localhost:8502 (not the numeric address), Settings, enter the existing vault password once, then Enable fingerprint / device unlock. For first-time setup enter the app credentials as well. A compatible platform passkey authenticator must return WebAuthn PRF output with user verification. The browser uses it to encrypt the existing password using AES-GCM with a fresh salt and IV; only ciphertext and credential metadata persist in origin-local browser storage. This is a local vault wrapper, not remote WebAuthn identity authentication. Screen-lock PIN or other device verification may be chosen by Android. Use the password fallback if PRF is unsupported or browser data is cleared; removal does not delete the original vault. Keep the original password for recovery. Device testing pending; no claim of verified fingerprint support on a particular handset. FYERS OAuth remains mandatory when the broker token expires. Keep the server loopback-only; the exact localhost host is additionally accepted, and POST Origin must match Host. Do not share browser/profile access or run multiple local servers concurrently.

### Cached startup and staged refresh
The phone browser saves the latest completed qualified-stock scan snapshot (cash/option values, call provenance, EMA/R1 and filter metadata) in origin-local storage, without credentials. On launch it renders that snapshot before broker access. After FYERS is connected it resumes an unfinished server scan or starts one fresh scan, retaining the displayed snapshot until the user taps Update now. A failed or partial refresh never replaces the last completed cache. Background batches continue across visible app tabs, not when the browser is hidden; all existing request pacing remains. No automatic recurring full scan after completion. Manual futures, strategy and option-chain views are separate and not cached by this change. Clearing site data removes cached results. The displayed timestamp is completion time of a multi-request snapshot, not a live quote timestamp. Only the latest completed scan is retained for the next launch. A stale displayed scan cannot drive a server-side R1 request.
